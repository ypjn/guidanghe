**模块职责：**
| 模块 | 职责 |
|---|---|
| `scanner.py` | 递归扫描目录，返回 `ScanResult` 数据类。零副作用，不创建任何文件或目录。|
| `main.py` | PySide6 界面：目录选择、后台扫描线程、文件表格、状态栏反馈 |

**扫描规则实现细节：**
- 使用 `os.walk(topdown=True, followlinks=False)`，原地修改 `dirnames` 阻止深入跳过目录
- 目录级跳过：`.git`、`_已整理`、`.organizer`、以 `.` 开头的隐藏目录、符号链接目录
- 文件级跳过：以 `.` 开头的隐藏文件、符号链接文件、无读取权限文件、非普通文件
- 权限错误和其他 OSError 不中断批处理，聚合到 `ScanResult.errors`

**界面技术：**
- `QThread` 后台扫描，避免阻塞主线程（V0.1 需求：扫描中界面保持响应）
- `QFileDialog.getExistingDirectory` 选择目录
- `QTableWidget` + `QHeaderView.Stretch/ResizeToContents` 自适应布局
- Fusion 风格 + 蓝灰色调 QSS

### 📋 人工观察与判断

1. **环境管理：** uv 管理的 Python 遇到 PEP 668 很常见，创建 venv 是正确做法，不应加 `--break-system-packages`。这一点已按设计文档要求遵守。

2. **扫描规则优先级：** 先目录级（.git/_已整理/.organizer/隐藏目录/软链接目录），再文件级（隐藏文件/软链接文件/权限），实现清晰。隐藏目录内的文件不会被扫描到（因为 os.walk 不进入隐藏目录），隐藏文件则在文件层面过滤。

3. **预览零副作用：** 本版是只读扫描，天然满足"零副作用"要求。后续 V0.2/V0.3 中生成整理计划时也必须保持这一点——**预览不能创建分类目录**。

4. **核心模块与界面解耦：** scanner.py 完全不依赖 PySide6，可以独立单测。这是好架构，后续版本如果需要更换界面框架或做 CLI 测试，无需修改核心逻辑。

5. **经验教训（来自 History 经验 #1386010）：**
   - ✅ 预览阶段零副作用（V0.1 天然满足，V0.2 需保持）
   - ✅ 先探测环境再决定依赖（没有假设 PySide6 已安装）
   - ✅ 单文件失败不中断批处理（scanner.py 中权限错误和 OSError 都是聚合而非抛出）

6. **下一步 V0.2 需要注意：** 分类规则、固定计划生成、同名处理——这些都要和扫描模块解耦，最好在 scanner.py 基础上扩展一个 planner.py 来生成不动文件的计划。

```
归档盒源码/
├── scanner.py     # V0.1 不变 — 纯逻辑扫描
```

**planner.py 核心组件：**

| 组件 | 职责 |
|---|---|
| `CourseRule` | 关键词列表 + 优先级 order + 课程名 |
| `DEFAULT_COURSE_RULES` | 6 条内置规则（高数/AIGC/线代/概率/物理/英语） |
| `MODE_BY_TYPE` / `MODE_BY_COURSE_THEN_TYPE` | 两种分类模式常量 |
| `PlanItem` | 单个计划条目（源信息 + 分类结果 + 目标路径 + 唯一名称） |
| `OrganizePlan` | 完整固定计划，含汇总和参数 |
| `_match_course()` | 按 order 排序后 first-match-wins |
| `_build_target_dir()` | 根据模式构造 `_已整理/{课程}/{类型}/` 或 `_已整理/{类型}/` |
| `_assign_unique_names()` | 同名冲突自动分配 ` (1)` ` (2)` 后缀；同时检查磁盘已存在目标 |
| `generate_plan()` | 主入口：从 ScanResult 生成 OrganizePlan |
| `parse_rules_text()` / `rules_to_text()` | 用户编辑文本 ↔ CourseRule 列表互转 |

**main.py 改造点：**

#### 阶段三：Bug 修复

**PlanItem dataclass 字段顺序问题：** 最初 `rule_index: Optional[int] = None`（有默认值）放在了 `target_dir_rel: str`（必填）之前，Python dataclass 要求所有必填字段在有默认值字段之前。修复：将必填字段集中放在前 7 行，可选字段（`rule_index`, `conflict_with_existing`, `selected`）放在最后。

#### 阶段三：核心设计决策

**1. SQLite 数据库位置**
固定在 `{root}/.organizer/history.db`。scanner.py 的 `SKIP_DIRS` 已包含 `.organizer`，扫描天然跳过——完美复用。

**2. 执行意图先持久化**
每条 action 在 executor.py 中写**两次**：
- 第一次：`storage.create_action(batch_id, item, idx, sha256)` → status=`planned`（移动前）
- 第二次：`storage.update_action(batch_id, idx, STATUS_MOVED/FAILED/SKIPPED)` → 更新结果
设计上是为 V0.5 进程中断恢复打基础：如果进程在第二次更新前被杀掉，重启后会发现 status=`planned` 的孤立动作。

**3. 批次状态机**
```
planning → executing → done / partial / partial_failed_undone
                              ↓
                         undone / partial_undone / partial_failed_undone
```
`get_pending_batch()` 只返回 status != undone 的批次，防止重开时误提示。

**4. 撤销器单一入口 `undo_latest_batch()`**
不重新计算任何路径，100% 依赖 SQLite 保存的 source_rel / target_rel / source_sha256。撤销前三项核验：
- 目标文件是否 still exists
- 目标 SHA-256 是否 still equals 移动时版本（≠ 用户修改）
- 原路径是否 still 空闲（≠ 被新文件占用）
任一不满足 → status=conflict，保留现状。

**5. 同名处理（目标已存在）—— planner 已经算好**
executor 不重新分配名称（违反"执行器必须使用固定计划"）。planner 在 V0.2 已经把目标已存在的情况处理好：给新文件分配 (1) (2) 后缀 + conflict_with_existing 标记。executor 消费的是完全固定的 `item.target_rel_path`。

### ✏️ 人工观察与判断

1. **Storage 打开策略：** 每切换目录打开新 Storage；关闭程序时 close。SQLite 用的是单进程（GUI 是单线程），没有 WAL 模式也不需要——数据库在 .organizer/ 下，每次 Storage(root) 连接同一个文件。

2. **跨批次隔离：** 不同 root 目录的 .organizer/history.db 独立——因为 Storage(root) 固定在 root/.organizer/ 下。这意味着你可以同时整理多个互不相关的目录，历史各自独立。符合设计文档"操作在所选根目录内部"的约束。

3. **Executor 和 Undo 的对称关系：** execute_plan 写入 `planned → moved/failed/skipped`；undo_latest_batch 读取 `moved` 的动作，逐个移回并写 `undone/conflict`。两者都是纯函数 + SQLite 副作用，可以独立测试。

4. **"执行意图先持久化"的实际验证：** executor.py 的 create_action 在任何文件系统操作前就写入 status=planned。如果进程在 os.rename 前被杀，SQLite 里会残留一条 planned 状态的 action —— V0.5 要处理这个。

5. **撤销器只移动本批次 moved 的文件：** 它不会扫描文件系统找"哪些可能是这批整理的结果"。全部依赖 SQLite 记录的 source_rel 和 target_rel。这是正确的——撤销是批次级操作，不是启发式猜文件归属。

6. **原版文件不受撤销影响：** 冲突场景中，原版（V0.1 残留在 _已整理/ 里的）文件不是本批次 action 列表的一部分，撤销不碰它。这个保护是正确的——"撤销 = 恢复本批次做的事"，不是"回滚整个文件夹到旧状态"。

7. **重复撤销防呆：** undo_latest_batch 在所有 moved 项已变 undone 时返回 restored=0，批次状态更新为 undone。重复调用无副作用。

8. **Scanner 回归确认：** 本轮没改 scanner.py，E2E 测试的扫描步骤输出和 V0.2 一致（跳过隐藏 1、.git 1），未受影响。

#### 阶段二：状态设计（先冻结状态常量，再实施）

新增状态常量：
| 常量 | 值 | 说明 |
|---|---|---|
| STATUS_CANCELLED | "cancelled" | 执行中取消的动作 |
| STATUS_PAUSED | "paused" | 恢复时状态不明确，暂停人工处理 |
| BATCH_CANCELLED | "cancelled" | 用户取消（有已完成项） |
| BATCH_CANCELLED_CLEAN | "cancelled_clean" | 用户取消 + 无一完成 |
| BATCH_RECOVERED_PARTIAL | "recovered_partial" | 恢复后仍有不确定项 |

动作状态转换图（核心）：
```
executing: planned → moved / failed / skipped / cancelled
恢复时:    planned → moved (补记)  / paused (状态不明确)
撤销:      moved / conflict → undone / conflict
```

#### 阶段三：recover_batch 的 5 类磁盘状态核对（核心设计）

对每个 status=planned 的动作，按 `(src_exists, tgt_exists, sha(tgt)==预期)` 组合分类：

| 情况 | src | tgt | sha | 判定 | 处理 |
|---|---|---|---|---|---|
| A | ✓ | ✗ | — | 还没执行 | 保持 planned |
| B | ✗ | ✓ | ✓ | 移动成功但日志没写 | **补记 moved** |
| C | ✗ | ✓ | ✗ | target 被人改过 | **paused 人工处理** |
| D | ✗ | ✗ | — | 什么都没了 | **paused 人工处理** |
| E | ✓ | ✓ | ✗ | src 还在 + target 也有别的文件 | **paused 人工处理** |

**关键原则：** recover_batch 不盲目重做、不盲目撤销、不盲目补记。状态不明确就暂停。

#### 阶段四：实施与真实 Bug 发现

**Bug — storage.update_action 的 if/elif 漏掉了新状态：**
- **现象：** 第一次跑 17 项只有 14 过。场景 1 取消后 `result.cancelled=4` 但 SQLite 里 status 仍是 planned。场景 2 恢复后批次状态不对。
- **根因：** storage.py 的 update_action 写死了 `if status in (MOVED, FAILED, SKIPPED)` 和 `elif status in (UNDONE, CONFLICT)`，新增的 STATUS_CANCELLED 和 STATUS_PAUSED 两个分支根本不会走到 UPDATE。代码直接 `if/elif` 跳过，然后 commit 空事务。
- **修复：** 改为通用 UPDATE 模板——用 executed_at/undone_at 的赋值来区分执行阶段 vs 撤销阶段，不再按状态类型分分支。
- **教训：** 扩展枚举类型时，**所有 switch/if-chain 必须同步覆盖新值**。不能假设"默认分支会处理"。这不是逻辑 bug，是遗漏 bug。

**Bug — recover_batch finalize 没考虑 still_planned：**
- **现象：** 场景 2 恢复后 item_a=moved + item_b=planned，finalize 判 moved>0 + 其他全 0 → BATCH_DONE。但 item_b 还没处理！
- **根因：** finalize 只计 moved/failed/skipped/cancelled/paused，漏掉了仍处于 planned 的动作。
- **修复：** 加 `planned_still` 计数：有 moved 也有 planned → BATCH_RECOVERED_PARTIAL；全 planned → BATCH_CANCELLED_CLEAN。
- **教训：** 状态机 finalize 逻辑要覆盖**所有**状态组合，尤其是"混合状态"（部分已移动 + 部分未处理）。

**修复前后场景 2 对比：**
| 环节 | 修复前 | 修复后 |
|---|---|---|
| storage.update_action 写 cancelled | ❌ 空事务跳过 | ✓ 通用 UPDATE 写入 |
| recover finalize (moved=1, planned=1) | BATCH_DONE（错误） | BATCH_RECOVERED_PARTIAL（正确） |

### ✏️ 人工观察与判断

1. **取消在当前文件操作结束后生效 — 正确语义：** execute_plan 的 cancel 检查在每个文件循环开头。os.rename 是原子操作，一旦开始就不会被 interrupt。下一个循环迭代前检查 cancel_event → break → 把 remaining 标记 cancelled。正好满足"单文件操作结束后生效"。

2. **recover_batch 的 5 类 case 来自真实思考：** 场景 B（src 消失 + tgt 在 + sha 匹配）就是需求明确要求的"rename 后写库前被杀"；case A/C/D/E 是自然分支。没有编造 case。

3. **recover_batch 不盲目"自动完成"：** case C/D/E 状态不明确时只标 paused，等用户人工处理后再决定。这符合"暂停该项并提示人工处理"的设计要求。

4. **二次 recover 幂等：** 同批次多次调 recover_batch 不会产生新的 moved/paused（recovered_moved=0, paused=0）。因为第一次 recover 已经把所有 planned/executing 状态处理完了，第二次读不到新的。

5. **storage.update_action 的通用 UPDATE 比 if/elif 更安全：** 原来的 if/elif 容易漏状态类型，改成一条 SQL 模板后，executed_at/undone_at 的赋值由状态类型决定，新增任何状态都不会漏掉 UPDATE 语句。这是防御性编程的好例子。

6. **进程中断恢复 ≠ 断电恢复：** 测试用 os._exit/simulated-rename 模拟的是"进程在可控点被终止"。真实断电/硬盘故障可能导致文件系统元数据损坏，这不在本轮覆盖范围（提示词明确区分）。

7. **V0.5 的"取消"目前只在 executor 层面，UI 还没接：** executor.py 的 execute_plan 已经支持 cancel_event 参数，但 main.py 还没加取消按钮。这是后续 UI 集成工作，核心逻辑已经就绪。

## 三、三个指定问题的根因、修复与证据

### 1. 计划线程刚结束时取消无效

- **根因**：`_cancel_plan_generation()` / `on_cancel_execute()` 以 `worker.isRunning()` 作为接受取消的条件。线程已结束、成功信号仍在事件队列时，按钮可见但取消被直接忽略，随后排队的成功结果被发布。
- **修复**：取消改为看界面相位（`_plan_working` + 当前 `seq`）。点击取消记录 `_plan_cancel_seq`、立即撤下已有计划并禁用执行；`_on_plan_done` 对同 `seq` 或已请求取消的结果直接丢弃；结束回调只负责结束生成相位并允许重新预览。
- **测试**：P7 通过断开 `finished_ok`、阻塞主线程 `worker.wait()` 精确复现「线程已死、结果未交付」；P8 复现「成功回调已处理、结束回调未处理」。两项均断言取消被接受、计划为空/无效、执行禁用、结束后可重新预览。

### 2. 请求关闭后扫描完成仍启动新计划

- **根因**：关闭等待只设置了 `_close_pending`，但 `_on_scan_done()` 仍走正常成功路径调用 `_generate_and_show_plan()`，且新 PlanWorker 未收到取消。
- **修复**：所有业务入口（扫描、计划生成、整理、撤销、保护配置、规则编辑）以及完成回调都检查 `_close_pending` / `_closing`；关闭等待期间不启用任何可启动任务的控件；迟到回调不重开数据库、不发布结果；线程结束后由 `_retry_close` 自动关闭。
- **测试**：P9 使用真实 `ScanWorker`（`scan_directory` 被门控阻塞）→ 请求关闭 → 放行扫描，断言未启动 PlanWorker、`_plan_seq_counter` 不变、数据库保持到线程结束、窗口自动关闭。S11/S12 在真实副本上分别验证扫描中关闭与计划生成中关闭。

### 3. V1.0 回归失败仍返回 0

- **根因**：`tests/test_v10_regression.py` 入口直接调用 `main()`，返回值被丢弃。
- **修复**：最终统计存在失败或未验证项时返回 1，全部通过且有用例时返回 0；入口改为 `sys.exit(main())`。
- **测试**：`tests/test_v10_exit_code.py` X1–X4 在独立子进程注入通过/失败/未验证三种结果，分别断言退出码 0 / 非 0 / 非 0，并保留注入证据；生产逻辑未为测试制造缺陷。

### 4. 验收中额外发现的真实缺陷：后台线程复用 SQLite 连接

- **发现场景**：S13「整理中关闭」首次运行时执行线程启动后立即失败，界面提示 `SQLite objects created in a thread can only be used in that same thread`，未产生任何批次。
- **根因**：`ExecuteWorker` / `UndoWorker` 直接复用主线程创建的 `Storage` 连接。
- **修复**：两个后台线程在 `run()` 内各自新建 `Storage(root)`，结束后在 `finally` 关闭；窗口只保留自己的连接。新增 P10 走真实界面「开始整理」→ 后台线程 → 撤销，断言批次、移动数、撤销数与源文件恢复。

## 一、旧清单为何可能漏检（根因）

`tests/scale_check.py` 旧版 `build_manifest(scan_result)` 的枚举来源是
`scan_result.files + scan_result.skipped`——即首次扫描登记过的路径集合。
它存在两个结构性盲区：

1. **登记之外的路径不可见**：清单建立后原目录新增的文件、`_已整理` 里
   意外残留的文件，从未出现在 `files/skipped` 里，清单比对永远是
   “多余 0、多重集合一致”。用户复现：扫描→建清单→新建 `extra.txt` 与
   `_已整理/leftover.txt`→用旧 `sr` 重建清单→比对仍通过（假阴性）。
2. **扫描器的合法跳过同样成为盲区**：生产扫描器按设计跳过隐藏目录
   （`.git`、`.venv` 等以 `.` 开头的目录）、`node_modules` 等依赖目录
   （`scanner.py` 的 `SKIP_DIRS`），这些目录内的文件不在
   `files/skipped` 里。旧清单因此无法核验这些区域是否被误动。
   本轮独立枚举实测：副本磁盘实际有 **199366** 个文件，
   而扫描登记路径只有 13483 条——差距约 18.5 万个文件全部是旧清单的盲区。

## 二、新方法：独立文件系统枚举

新增 `tests/manifest_tool.py`（验收专用，独立于生产扫描器/计划/数据库）：

- `fs_manifest(root)`：`os.walk(root, topdown=True, followlinks=False)`
  直接从文件系统枚举，**不复用** ScanResult、OrganizePlan 或数据库动作列表。
- 排除规则显式且唯一：仅排除 `{root}/.organizer`（程序自身运行记录：
  `history.db`、`protect_config.json`），用户文件一律纳入。
- 符号链接（文件/目录）不跟随，记录为 `["link", 链接目标]`；
  指向目录的链接不下降，不会越界枚举到根目录之外。
- 只记录文件与链接，不记录目录；**空目录不计入**，
  保留“撤销后允许残留空父目录”的既有边界，不误判为丢失或多余。
- `getsize/readlink/open/SHA-256` 失败记入 `errors` 并判核验失败，
  不静默忽略。
- `dup_stats()` 分别输出**重复组数**（出现次数>1 的指纹个数）与
  **组内文件份数**（这些组包含的文件总数）。

`scale_check.py` 在 S2（执行前）、S8（正常撤销后）、S14（全部取消/关闭
测试结束后）三个时点分别独立枚举，清单保存到副本之外。

## 二、历史刷新缺陷：根因、修复与前后证据

**根因**（三处叠加）：
1. `on_history()` 复用已创建窗口时只调 `_reload()`；
2. `_reload()` 只更新批次列表，不重读逐项动作；
3. `_on_batch_selected()` 遇到相同 batch_id 直接早退，手动「刷新」
   （旧实现连接到 `_reload`）也不会更新明细缓存。
   交互 009 的 `refresh_after_change()` 修复只覆盖「历史窗口持续可见」路径。

**修复**（统一刷新逻辑，`main.py`）：
- `HistoryDialog.refresh_all()`：统一刷新入口 = 重读批次列表
  （`_render_batches(keep_selection=True)`，批次消失时自动改选首行）
  + 强制重读选中批次逐项动作（`load_items(force=True)`）；
- `_load_items()` 更名 `load_items(force=False)`：force 时即使 batch_id
  未变也重读数据库；
- 「刷新」按钮改连 `refresh_all()`；`on_history()` 复用窗口时调用
  `refresh_all()`；`refresh_after_change()`（工作完成自动刷新）同样走
  `refresh_all()`；核对恢复结束后重看历史走同一入口；
- 搜索关键词、状态筛选、页码在刷新时保留；页数减少时 `_render_items`
  把页码校正到最后一页；读取失败时 `_show_error` 清理缓存与展示并
  刷新按钮。

**修复前证据**（用快照代码独立复现，`/tmp/_v12r2_repro_before.py`）：
```
关闭前明细状态      = 已移动
撤销后数据库实际    = undone
重开后批次列表状态  = 已撤销（列表已更新）
重开后明细状态      = 已移动      ← 过期
手动点刷新后明细    = 已移动      ← 刷新无效
缺陷复现            = 成功：明细过期，刷新无效
```

## 三、H9 假阳性勘误（不改写旧记录，如实追加）

交互 009 的 H9「中断批次：历史页核对恢复可用，恢复后按磁盘实际回滚」
**验证不充分**：旧测试只在数据库手写 moved/planned 状态、源文件从未真实

本就存在）。用户把 `recover_batch` 替换为空操作后，H9 与整 18 项仍然
通过。**交互 009 中「H9 通过」的结论不能作为恢复功能的有效验收证据，
本节为勘误。**

**H9 重写**（H9a–H9f，真实文件移动 + 真实 SHA-256）：
- H9a 移动已发生状态未写回：恢复前源不在/目标在；核对后补记 moved

- H9b 尚未执行：核对后保持 planned，不自动移动；
- H9c 状态不明确：目标内容不符 → paused（「≠ 预期」）/ 源目标同存 →

- H9e 恢复后重看历史：列表与明细均为数据库实际状态；
- H9f 后续独立撤销：已确认 moved 项路径与内容恢复；paused 项保持现状
  （恢复与撤销职责分离：恢复只核对/补记/暂停，撤销才移回文件）。

**空操作反例**（`tests/_v12r2_noop_check.py`，独立进程，注入结果与正常

## 四、核对恢复后台化（实现说明）

- 新增 `RecoverWorker(QThread)`：复用唯一的 `recover_batch` 核心逻辑
  （`executor.py` 仅增加可选 `progress_cb(checked, total, path)`，
  统计口径=待核对 planned/cancelled 动作数，兼容原调用）；线程内自建
  自关 Storage，不复用主线程 SQLite 连接；信号携带 seq+root，回调校验
  来源，迟到结果丢弃。
- 三个入口（启动检查、切换目录检查、历史页按钮）统一走
  `MainWindow._do_recover()` → 后台 RecoverWorker；开始前进 TaskContext
  （kind=recover，不可取消，不显示无效取消按钮）；进度显示
  「正在核对 [n/m]（按待核对动作数统计）+ 当前路径」。
- 结果返回（`_on_recover_done`）与线程真正退出（`finished` →
  `_finish_task`）分别处理；文案区分「核对完成 / 补记已移动（其余仍未
  执行）/ 仍未执行 / 暂停待人工确认」；失败（`_on_recover_failed`）
  明确报错、批次保持原状可复核，不误报成功。
- 关闭行为：恢复运行中请求关闭 → 窗口进入关闭等待（RecoverWorker 已
  纳入 `_background_workers`）→ 禁止新业务任务 → 等线程自然结束 →
  线程内连接已关 → `_retry_close` 自动关闭主窗口连接与窗口；关闭等待
  期间业务结果弹窗被抑制（结果仍写入状态栏与数据库）。
- 文案修正：历史页「核对恢复」确认对话框与结果弹窗不再使用
  「恢复确定的项目」这类易被理解为自动回滚的表述，明确说明
  「核对过程不会移动文件；放回原位置请使用撤销」。

## 二、修改前梳理（实际代码）

- 推荐模式 `MODE_BY_DIRECTION_SEMESTER` 原来在 `planner._match_by_context`
  中使用代码内固定映射：学期、顶层方向、学期内目录、关键词、`附件-`
  前缀；用户无法修改。
- 「编辑课程规则…」只写入 `MainWindow.rules`，仅被

- 默认映射全部写在 `planner.py` 常量中，且 `_match_by_context` 直接
  读取全局默认对象。

结论：需要把这些常量转成独立配置对象，同时让推荐模式只接收显式配置；
默认值与匹配顺序必须逐条保持，避免改变既有路径结果。

## 三、实现

### 1. 新模块

| 文件 | 职责 |
|---|---|
| `classification_config.py` | 配置数据类、默认配置工厂、校验、原子读写、损坏/版本/根目录处理、匹配核心 |
| `config_dialog.py` | 推荐模式规则编辑器（五张表、启停/排序/增删、恢复默认、试运行入口） |
| `rule_preview.py` | 影响预览纯函数 + 后台线程（seq+root 校验） |

### 2. 配置结构（version=1）

保存位置：`{根目录}/.organizer/classification_config.json`

```json
{
  "version": 1,
  "root": "/绝对/根目录",
  "updated_at": "2026-11-08T...",
  "semester_map":      [{"source": "大二上", "semester": "2026秋-大二上", "enabled": true}],
  "top_direction":     [{"source": "Code", "direction": "项目", "enabled": true}],
  "semester_dirs":     [{"semester": "大二上", "source": "数据结构",
                          "direction": "课程", "category": "数据结构", "enabled": true}],
  "generic_dirs":      [{"prefix": "附件-", "direction": "校园事务",
                          "category": "通知", "enabled": true}],
  "keyword_rules":     [{"keywords": ["高数"], "target": "高等数学",
                          "direction": "课程", "scope": "path",
                          "trigger": "subdir", "enabled": true}]
}
```

- 数组顺序即优先级；`enabled=false` 的规则跳过。
- `semester_dirs.semester` 关联**学期标签**（不是来源目录名），因此
  自定义“来源目录名 ≠ 学期标签”时也能命中。
- `keyword_rules.scope`：`filename` / `path`；`trigger`：
  `subdir`（仅类别留空的目录映射）或 `unmatched`（仅将进入待定时）。

### 3. 校验与安全

- 字段类型、非空、方向枚举、匹配范围/触发场景枚举、重复来源/重复
  目录/重复关键词、学期标签必须已登记；错误信息带“第 N 条”与原因。
- 目标/学期/目录名拒绝 `/`、`\`、`..`、`.`、绝对路径、`~`、盘符、
  控制字符；保存前校验，不合法不写盘。
- 默认配置每次 `default_config()` 新对象，不修改全局默认；
  与默认完全一致时保存会删除自定义文件（恢复默认）。
- 原子保存：同目录临时文件 + `fsync` + `os.replace`；失败删除临时
  文件并抛错，旧文件不变。编辑器保存失败时留在对话框并提示，不会
  显示“已保存”。
- 损坏/版本不兼容/根目录不匹配/字段非法：抛
  `ClassificationConfigError`，保留原文件；推荐模式**停止生成计划**，
  不静默回退默认后继续执行。用户可打开编辑器用默认草稿修复，
  只有明确保存才覆盖原文件。

### 4. 分类与计划

- `planner.classify_entries()` 成为唯一分类+路径构造入口；
  `build_plan(compute_duplicates=False)` 供试运行，`generate_plan`
  供正式计划，两者共用同一逻辑。
- 推荐模式固定匹配顺序：学期映射 → 顶层方向 → 学期内目录
  （类别留空时关键词细分）→ 通用目录前缀 → 未登记目录锚定 →
  待定（可选 unmatched 关键词兜底）。每条 `PlanItem` 新增
  `rule_key`（如 `semester_dir:大二上/数据结构`）。
- 未匹配进入 `_已整理/待定/…`，不猜测。
- 计划生成开始时深拷贝配置快照，后台线程不引用编辑器草稿；
  保存配置会递增计划 seq 并清空旧计划，迟到结果被丢弃。
- `OrganizePlan.config_snapshot` 随批次写入数据库，历史可解释。

### 5. 存储迁移

- `batches` 新增 `config_json TEXT DEFAULT ''`；打开旧库时按
  `PRAGMA table_info` 只增列，不改旧字段含义。旧批次
  `config_json=''`，历史显示为空；旧记录仍可读、可撤销。
- 历史窗口选中批次后显示“本批次实际使用的分类配置（快照）”。

### 6. 界面

- 新增「推荐模式配置…」按钮；「编辑课程规则…」只在
  「按课程再按类型」可用，配置按钮只在「推荐」可用，避免
  “能编辑但当前模式不使用”。
- 主窗口配置状态标签显示：内置默认/本目录自定义、各表条数、
  只影响推荐模式；配置错误时红色提示并说明已阻止生成计划。
- 编辑器：五张表、启用勾选、上移/下移、添加/删除、恢复默认、
  “试运行／查看影响…”、保存并应用/取消；独立草稿，取消不改变
  生效配置。
- 试运行结果窗口：数据范围/样本数、各规则命中数、未匹配数、
  前后分类与目标变化、代表性文件；明确标注“未计算 SHA-256”。

## 二、根因、反例与修复

### 1. 关键词规则方向不生效

根因（`classification_config.classify_context`）：类别留空目录命中
关键词规则时，返回的 `ContextMatch.direction` 使用了目录映射的
`rule.direction`，却用关键词规则的 `target` 作为类别；因此界面
依据写成“项目/机器人实验”，实际方向仍是“课程”，最终进入
`_已整理/课程/…`。默认关键词规则方向本来就是“课程”，所以默认
配置结果未暴露此问题。

修复：该分支的方向改用 `kw_rule.direction`；目录映射方向只用于
关键词未命中时的兜底。路径模板未改动。

反例（用户提供，合成场景）：`大一下/已完成期末/robot.pdf`，
“已完成期末”→课程/类别留空；新增 robot 关键词→项目/机器人实验/
filename/subdir。修复后正式计划与试运行均为：

- 方向=`项目`，类别=`机器人实验`
- 目标=`_已整理/项目/机器人实验/robot.pdf`
- 依据=`学期「大一下」/「已完成期末」+关键词「robot」→ 项目/机器人实验`

默认关键词 `高数` 的既有路径
`_已整理/课程/大一下/高等数学/文档/高数/f.pdf` 保持不变。

### 2. 配置读取时类型转换绕过校验

根因（`classification_config.load_config`）：先做版本比较/字段转换，
`bool("false") → True`、`str(2026) → "2026"`，且 Python 中
`True == 1`，导致 `version: true` 通过版本检查。主窗口因此把非法
文件当成合法自定义配置并允许生成计划。

修复：新增 `validate_config_payload()`，在版本比较与任何转换之前
按原始 JSON 类型校验：

- `version` 必填、必须是整数，明确排除布尔值；
- `root` / `updated_at` 可缺省，出现时必须是文本；
- 五个规则数组可缺省（视为空），出现时必须是数组，元素必须是对象；
- 每条规则按结构校验必填/可选文本字段；`enabled` 出现时必须是
  真正的 JSON 布尔；`keywords` 必须是文本数组且元素均为文本；
- 同版本未知额外字段仍忽略；
- 错误带数组序号与字段名（如 `semester_map 第 1 项：字段 enabled ...`）；
  原文件保留，推荐模式记录 `_config_error` 并阻止生成可执行计划。

`config_from_dict()` 同样先调用该原始类型校验，避免其他调用方绕过。
合法 `false`、空规则数组与现有默认配置均正常加载。

### 3. 关闭等待期间仍发布试运行结果

根因（`config_dialog`）：成功信号已排队但线程未退出时关闭主窗口，
主窗口已进入 `_close_pending`，而 `_source_ok()` 只校验编辑器自身
`_closed`、seq 与 root，未校验主窗口关闭状态；排队回调仍会调用
`ImpactPreviewDialog.exec()` 并恢复控件。

修复：`_source_ok()` 增加 `_host_closing()`（读取主窗口
`_close_pending` / `_closing`）。关闭等待期间结果、失败、进度和
取消回调全部忽略：不弹成功/错误窗口、不恢复可启动新任务的控件。
线程结束后的 `finished` 回调仍执行注销与引用释放；主窗口登记表接管
最终注销，即使编辑器已关闭也不会漏清理。

### 4. 取消编辑时同步等待

根因（`config_dialog.reject`）：界面线程调用 `_worker.wait(5000)`；
门控线程下实测阻塞约 5 秒且 Qt 心跳为 0，返回时线程仍在运行。

修复：`reject()` 改为 `request_cancel()` + 立即关闭，不再 `wait()`；
线程不挂在对话框下，由主窗口 `_rule_preview_workers` 保活，`finished`
后异步注销并释放引用。迟到结果/进度/失败因 `_closed` 与主窗口关闭
状态被忽略。未使用 `terminate()`、强杀或 `processEvents()` 忙等。

# 交互 016 — V1.5 保存为长期规则（2026-11-09 晚）

## 一、用户诉求

以 V1.4 单文件分类修正的修补版为基线，完成"保存为长期规则"：
用户纠正一个文件后，能把这次判断固化成规则，让后续符合条件的文件自动采用相同分类；
规则要能按明确的优先级真正生效（覆盖已命中的原有映射），并支持查看/编辑/禁用/删除/排序、
按根目录隔离、重启后保留、历史可追溯。

本轮以功能开发为主，只做必要的针对性验证；全面审核、大目录验收与跨平台测试留到功能冻结后。

## 二、优先级与匹配语义

```
当前计划的临时手动修正（plan_patch，计划内存态）
        ↓
已启用的长期修正规则（按配置顺序，取第一条命中）
        ↓
原有推荐模式映射（学期 → 顶层方向 → 学期内目录 → 通用前缀 → 未登记锚定 → 待定）
```

- 长期规则在 `planner.classify_entries` 内、`classify_context` 之后应用，
  因此**能覆盖**已经命中学期/课程映射的文件（T03 实测）。
- 保护目录仍由 `protect_config` 独立判定，任何分类规则都不能解除保护。
- 匹配方式只有三种，无正则/脚本：
  - `exact_path`：来源相对路径精确匹配（默认）
  - `dir_scope`：来源目录范围 + 是否包含子目录
  - `filename_keyword`：文件名关键词，可限定来源目录
- 目录匹配一律按**路径组件边界**比较（`dirs[:n] == scope`），
  「课程A」不会命中「课程AB」，「数据结构」不会命中「数据结构实验」。
- 内部路径三种处理：`keep`（保留自动结果）/ `clear`（清空）/ `replace`（用规则指定），
  避免把示例文件的内部路径无说明地套用到全部命中文件。

## 三、配置版本与兼容策略

- `CONFIG_VERSION = 2`，新增 `long_term_rules` 数组；`SUPPORTED_READ_VERSIONS = (1, 2)`。
- 读入时统一规范化到 2：旧配置（v1，无长期规则）可正常加载，保存时自动升级。
- 写入端一律写 2：旧程序读到新文件会因版本不兼容被拒绝并保留原文件，

2. `_on_save` 在校验后直接用 `self._previewed_rule` 覆盖当前草稿，

### 修复（`plan_patch.py`）

- 新增 `_rule_signature(rule)`：只比较业务字段（名称、匹配方式、来源、

- 试运行失败/取消时一并清空 `_previewed_rule`，避免“缓存只剩影响、没有规则”。

## 三、问题二：进程退出阶段 139（Qt 退出清理时序）

### 证据

用户提供的两次日志：
- `/tmp/archive_v15r2_test_v15_long_term_rules.py.ewDDCB`
- `/tmp/archive_v15r2_isolated.qWDfRp`

两次均为：先打印“合计 15 项：通过 15…退出码 0”，随后在解释器退出阶段
崩溃。栈：

```
destroyQCoreApplication
  → Shiboken::BindingManager::visitAllPyObjects
    → PySide::destructionVisitor
      → QPushButtonWrapper::~QPushButtonWrapper
        → QWidget::~QWidget → QObject::~QObject → SIGSEGV
```

其中一次还出现 `QObject: shared QObject was deleted directly.
The program is malformed and may crash.`

### 定位结论（如实）

- 崩溃发生在 `Py_Finalize → atexit → SbIQtCoreModule___moduleShutdown`
  → Qt 统一清理，**不是断言执行期**；与“线程已结束 / 登记表为空”
  不是同一件事：T15 证明线程已回收，但控件 Python 包装仍留到退出阶段。
- 本套件连续构造多个 `MainWindow` / `HistoryDialog` / `RuleDraftDialog`，
  只 `close()` 不销毁；解释器退出时由 Qt 统一清理父子控件，
  析构顺序不稳定，命中 `QPushButton` 时崩溃。这是退出期生命周期问题。
- **本机未稳定复现**：修复前直接运行套件 10+ 次、多种最小组合
  （仅规则草稿、试运行中途关闭、主窗口+历史、提前释放 QApplication、
  子控件悬挂）均为退出码 0。说明该崩溃是时序/环境相关，不能用
  “本次跑通”否定用户日志。

### 修复

1. `main.py` 新增 `shutdown_widgets()`：在 QApplication 仍存活时
   `close + deleteLater` 所有顶层窗口，并处理 `DeferredDelete`；
   入口在 `app.exec()` 返回后调用它，再退出。
2. `tests/test_v15_long_term_rules.py` 在汇总后调用同一函数，
   把“交给解释器清理”改为“应用存活时确定性清理”。
3. `plan_patch.RuleDraftDialog._release_worker`：线程结束后断开
   `finished` 连接并 `deleteLater()`，消除
   「线程→信号→闭包(lambda)→线程」引用环，避免 QThread 被拖到退出阶段回收。

未采用：关闭 GC、强制 `os._exit`、忽略返回码、删用例、单纯加延时——

## 二、问题与修复

### 1. 方案标识可越界写出方案库目录（生产代码缺陷）

反例：导入方案 `scheme_id="../escaped"` 被直接拼进文件路径，

### 3. 手动修正后方向筛选项未刷新（生产代码缺陷）

## 二、重复文件：范围、分组与缓存语义

- 范围：当前整理空间、当前扫描纳入的文件；不宣称核对整块硬盘，
  不包含保护/排除区域。
- 分组：
  - 内容重复：SHA-256 已核对且一致，组内 ≥2；
  - 同名不同内容：同名、全部成员已核对且存在不同指纹；
  - 同名（待核对）：同名组存在未核对成员；
  - 待核对/核对失败：缺失指纹、读取失败、文件消失，不作重复证据。
- 统计区分“组数”和“组内文件份数”；大小只表示文件大小。
- 指纹复用与失效：
  - 优先复用有效计划中已算指纹；
  - 扫描记录新增 `FileEntry.mtime_ns`；文件大小或修改时间变化 →
    旧指纹作废、后台重新计算；
  - 未算指纹时后台读取内容；
  - 整理、撤销、重新扫描、重新生成计划、切换根目录、配置变化后
    旧结果失效并关闭窗口。
- 后台线程：`DuplicateCheckWorker`（QThread）带 seq+root，
  进度/成功/失败/取消/结束信号；主窗口纳入 `TaskContext`
  （kind=duplicates）与 `_background_workers`，关闭时等待线程。
- 只读：不删除、不合并、不移动、不改勾选；打开/定位前检查存在性。

## 三、日常入口：最近空间、清单与根目录归属

- 最近空间：
  - `recent_spaces.py`，存放于系统用户配置目录
    `归档盒/recent_spaces.json`，与方案库共用 `app_data_dir()`；
  - 记录路径、名称、最近打开（微秒级）、固定状态；
  - 排序：固定优先，其次最近打开；
  - 缺失目录只标记“不存在或设备尚未挂载”，不自动创建；
  - 移除只删除记录，不删目录/配置/历史；
  - 属于本机状态，不进入方案文件或 Windows 交接包。
- 待整理清单（`intake_model.py`）：
  - 文件/目录登记；规范化 realpath；
  - 同项去重、子项被目录覆盖、后加父目录合并子项；
  - 未选空间：单个目录作为候选根由用户确认；文件拒绝；
  - 空间外来源明确拒绝，不静默设共同父目录；
  - 解析到扫描结果：只纳入清单内文件；受保护/未扫描/无效来源分别说明。
- 扫描与计划：
  - 保留整空间扫描；新增「扫描清单范围」；
  - `_effective_scan_result()` 用清单解析过滤扫描文件，
    计划只包含清单范围；
  - `_plan_scope_note` 显示“清单 N 项 → 纳入 M 个文件”；
  - 执行确认显示本次范围；
  - 清单变化时 `_invalidate_for_scope_change()`：旧计划失效，
    保留整空间扫描供重新预览；
  - 忙碌/关闭等待期间禁用最近空间、清单、清单扫描、重复文件入口；
  - 主窗口支持拖放加入；不移动文件、不写历史。

## 六、已知限制与未测项

- 重复文件只读：不提供删除/合并/自动勾选/释放空间；
