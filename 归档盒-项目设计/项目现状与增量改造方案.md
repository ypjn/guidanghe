#### 扫描与目录保护

- **扫描**：`scanner.scan_directory(root, ...)` 生成 `ScanResult`（文件列表 + 根标记）。跳过 `.organizer` 等内部目录。
- **目录保护**：`protect_config.py` 定义保护目录；保护目录内文件不进入计划。保护配置变更后旧扫描与旧计划全部失效（`main.py:3531`），必须重新扫描。
- **实测**：`test_review_followup_20261113.py` 验证子项目仍跳过、临时副本处理。✅

#### OCR（图片文字识别）

- **触发**：用户勾选「识别图片文字」后，在 `PlanWorker.run`（`main.py:329-342`）中调用 `ocr_engine.collect_image_text(scan_result.files, ...)`。
- **读取什么**：仅位图（`.png .jpg .jpeg .bmp .tif .tiff .webp .heic`），≤25MB，结果截断到 8000 字符。**图片不上传**，纯本地识别。
- **引擎优先级**：macOS Vision → Windows 系统 OCR → RapidOCR（本地模型，首次需联网下载）。
- **结果用途**：`ocr_texts` 传入 `generate_plan`，供分类规则匹配关键词；OCR 失败的条目触发 AI 回退。
- **缓存**：按 `(abs_path, mtime_ns, size)` 缓存，上限 512；引擎失败冷却 300 秒后可重试。
- **实测**：`test_ocr.py` 通过（exit 0）。✅

#### 分类与计划生成

- **入口**：`planner.generate_plan(scan_result, mode, rules, config, ocr_texts, ocr_errors)`。
- **模式**：`MODE_BY_TYPE`（按类型）、`MODE_BY_DIRECTION_SEMESTER`（按方向/学期）、`MODE_BY_COURSE_THEN_TYPE`（按课程再按类型）。
- **规则优先级**：临时手动修正 > 长期规则 > 原有推荐映射（学期/方向/目录）。
- **长期规则匹配**：`classification_config.match_long_term_rule(rel_path, compiled)`，按配置顺序返回第一条命中；命中后 `rule_key = "long_term:{rule_id}"`。
- **单文件修正**：`plan_patch.apply_override_to_plan(plan, source_rel, params)`，仅改当前计划条目，`is_manual_overridden=True`，不写回配置。
- **目标目录**：优先映射到现有学期/方向目录（`_build_target_dir_v2`），新建目录记录到 `created_dirs` 供撤销清理。

#### AI 回退（DeepSeek）

- **触发条件**（`ai_fallback.needs_ai`）：分类结果为「待定」或 OCR 失败；非手动修正；非 `MODE_BY_TYPE`。
- **何时触发**：`generate_plan` 之后、预览发布之前（`main.py:358-364`），对待定项逐一询问。
- **发送字段**（`ai_fallback._user_text`）：文件名、相对路径、文件类型、OCR 文字（截断 1200 字）或 OCR 失败说明；外加可选分类清单（来自现有规则，AI 不能新造目录）。
- **请求体**：`POST {base_url}/chat/completions`，`model=deepseek-chat`，`temperature=0`，仅文字（`with_image=False`，不发图片）。
- **安全限制**：默认关闭、无内置密钥；密钥存 `{app_data}/ai.json`（chmod 0600 / Windows icacls 限当前用户）；AI 输出必须是清单内 `{direction, category}`，否则丢弃。
- **缓存**：按 `(mode, rel_path, size, mtime, ocr_text[:200], len(pairs))` 缓存，上限 512，重新预览时复用。
- **实测**：`test_ai_fallback.py` 通过（exit 0）。✅

#### 批次确认与执行

- **确认对话框**：`main.py:531` `ConfirmDialog`，显示根目录、模式、已选/总数、手动修正数、目标目录、冲突警告；按钮「确认开始整理」。用户点 OK 才执行。
- **执行核验**（`executor.py:239-268`），逐项在移动前校验：
  1. 源文件不存在 → 跳过「源文件已不存在」
  2. 源文件无法读取（权限/占用）→ 跳过「无法读取源文件内容（权限/占用）」
  3. 源文件 SHA-256 与预览时不一致 → 跳过「源文件内容已变化」
  4. 目标路径已存在 → 跳过「目标路径已被占用」
  5. 通过后创建目录（记录到 `created_dirs`）、原子移动、更新动作状态。
- **持久化顺序**：先 `create_batch` + `create_actions_bulk`（意图入库，status=planned），再移动，再更新状态。中断后可恢复。

#### 历史、撤销与中断恢复

- **历史**：`storage.list_batches` 读取 `history.db`，显示批次状态、规则依据、手动修正/长期规则命中数。
- **撤销**：`executor.undo_latest_batch`，按动作记录把文件移回源路径，清理本批次创建的空目录。批次含 `planned/paused` 条目时拒绝撤销（状态未确定）。
- **中断恢复**：`executor.recover_batch` 对 `planning/executing` 批次的 `planned` 动作，按磁盘实际状态 + SHA-256 核对：
  - 源不在、目标在且 SHA 匹配 → 补记 `moved`
  - 源在、目标不在 → 保持 `planned`（可继续）
  - 其他组合 → `paused`（暂停人工处理）
- **实测**：`test_v17_combined.py` 验证完整流程+撤销；`test_review_followup_20261113.py` 验证中断后可继续撤销。✅

## 四、阶段 1 与阶段 2 最小改造方案

### 阶段 1 · 智能整理 MVP

**目标**：在现有扫描→分类→预览流程中，加入「文件正文 + 目录上下文」分析，生成带依据的结构化建议，少量提问歧义。

#### 4.1 正文与目录上下文分析接在哪里

- **接入点**：`PlanWorker.run`（`main.py:322`），在 OCR 之后、`generate_plan` 之前，新增一个 `extract_context(scan_result, ocr_texts)` 步骤。
- **复用模块**：
  - `scanner.py` 的 `FileEntry`（已有 `rel_path`、`size`、`mtime_ns`）。
  - `ocr_engine.py` 已能取图片文字；正文解析需新增轻量提取器（`.txt/.md` 直读，`.pdf/.docx` 按可用性降级，二进制跳过）。
  - `intake_model.py` 的范围解析可复用「目录上下文」（同级目录名、父目录名）。
- **输出**：为每个文件补充 `context_text`（正文摘要 + 目录路径关键词），传入 `generate_plan` 的规则匹配和 AI 回退。

#### 4.2 模型如何输出带依据的结构化建议

- **复用** `ai_fallback.py` 的请求/解析框架，但扩展输出 schema：
  ```json
  {"direction":"课程","category":"高等数学","evidence":"正文含「极限」「导数」；位于大二上目录","confidence":0.8}
  ```
- **校验**：`parse_choice` 扩展为校验 `direction/category` 在清单内 + `evidence` 非空；非法输出丢弃，保留待定。
- **接入预览**：`_apply_choice` 已能写 `rule_applied`（如「AI（图片文字没有命中规则）→ 高等数学」），新增 evidence 字段直接拼入 `rule_applied`，预览表格的「分类依据」列即可显示。

#### 4.3 哪些歧义值得向用户提问

- 仅对**会实质改变结果**的歧义提问：同文件名跨课程、正文与目录名冲突、多个高置信候选（confidence 差 < 0.1）。
- 提问形式：在预览中标注「待确认」行，用户可点选目标或跳过（跳过则保持原位/待定）。
- **不复用**现有 `ConfirmDialog`（那是执行确认）；新增轻量歧义确认面板，与预览同屏，不阻断其他文件的预览。

#### 4.4 建议如何进入现有预览和执行流程

- 结构化建议 → 写入 `PlanItem` 的 `direction/category/target_dir_rel/rule_applied`（同 `_apply_choice`）。
- 建议条目进入预览表格后，**仍需用户最终批次确认**（`ConfirmDialog`）才执行——不绕过边界 1。
- 未确认的歧义条目默认不勾选，不进入执行批次。

#### 4.5 阶段 1 验收场景

混合样本（课程资料 + 项目文档 + 下载文件）能生成草案；相同/模糊文件名能用正文或目录上下文区分；非法目标和未确认草案不触发文件修改。

### 阶段 2 · 个性化记忆闭环

**目标**：区分一次性修正与已确认长期偏好，SQLite 持久化偏好，两轮样本证明偏好复用。

#### 4.6 一次性修正 vs 已确认长期偏好如何区分

- **现状**：单文件修正（`apply_override_to_plan`）只改内存计划，`is_manual_overridden=True`，不写配置；长期规则经 `RuleDraftDialog` 确认后 `save_config` 写入 `classification_config.json`。
- **改造**：在单文件修正对话框（`plan_patch.OverrideDialog`）明确两个按钮：
  - 「仅本次」→ 走现有 `apply_override_to_plan`，不持久化。
  - 「保存为长期偏好」→ 走现有 `RuleDraftDialog` → `save_config`，并标记 `rule_key="long_term:{rule_id}"`。
- **区分标识**：`ActionRecord.rule_key` 以 `long_term:` 开头 = 长期偏好；`is_manual_overridden=True` 且无 `long_term:` = 一次性。历史页 `classification_source` 已能区分「手动/长期规则/自动」。

#### 4.7 SQLite 如何保存和检索偏好

- **现状**：长期规则存在 `classification_config.json`（每个根目录一份），非 SQLite。
- **方案（二选一，推荐 A）**：
  - **A（最小改动）**：沿用 `classification_config.json` 存长期规则（已有 `load_config`/`save_config`/`match_long_term_rule`），SQLite 的 `actions.rule_key` 仅做历史追溯。检索偏好 = `compile_config(config).long_term`，按优先级匹配。
  - **B（阶段 5 再考虑）**：把长期规则迁到 SQLite `preferences` 表，支持跨根目录复用。阶段 2 不做，避免破坏现有 `classification_config` 的根目录隔离语义。
- **检索**：`generate_plan` 已在分类时调用 `match_long_term_rule`，偏好自动生效；无需新增检索接口。

#### 4.8 如何用两轮不同样本证明偏好确实改变了下一轮建议

1. 第一轮：样本 A 中某文件被自动归错，用户「保存为长期偏好」（如「开发文档按项目归档」），确认规则写入 `classification_config.json`。
2. 重启程序（清空内存），加载样本 B（同项目的新文件，文件名不同）。
3. 验证：`match_long_term_rule` 命中该规则，`PlanItem.rule_key` 以 `long_term:` 开头，目标目录与偏好一致。
4. 对照：未保存偏好的同类文件仍走自动分类；一次性修正（仅本次）的文件在第二轮不体现该修正。
- **复用测试框架**：`test_v15_long_term_rules.py` 已覆盖规则保存与匹配，新增两轮样本断言即可。

#### 4.9 阶段 2 验收场景

先确认「开发文档按项目归档」，重启后加入同项目新文件，建议体现该偏好；单次修正和未确认候选不影响下一轮。
